# Part 2 verification

This work started from the imported published-theme baseline at commit `406dcea`. The feature implementation is commit `380c8a3`. No live Shopify theme was published or changed. I pushed that feature commit to the unpublished development theme `158335795338`, Development (24d837-Vinses-MacBook-Pro), and used its authenticated Draft preview for the browser checks below. The isolated checkout has no package manifest, so there are no project lint or typecheck commands. Theme Check reports 0 errors with 9 existing warnings across 155 files, and `git diff --check` passes. The current VM suite passes 8 of 8 tests. The added Escape regression fails against `380c8a3` because `handleKeydown` does not exist there, then passes with the local fix. The earlier 7 checks fail against `406dcea`; this shows the fixes and safeguards are absent from the imported baseline, not that every test is a separate baseline regression.

The first seeded issue sent the wrong variant to cart from quick add. In Safari, selecting Pair at 139 on Assessment Single and Pair Options put Single at 79 in the cart. This showed the wrong variant and cart price; no checkout or charge was performed. `assets/product-info.js` refreshed the display but did not refresh the hidden product-form variant input, so it retained the first variant ID. The fix calls the existing `updateVariantInputs` method during each valid variant update. `snippets/buy-buttons.liquid` renders the selected price beside Add to cart. The actual-method VM test calls `ProductInfo.handleUpdateProductInfo`: baseline source leaves the input as Single, while changed source sets it to Pair. A second actual-method test verifies that the selected submit price changes from `$10.00` to `$8.00`. In the Draft preview at desktop width, selecting Pair showed `$139.00` and adding it created exactly one Assessment Single and Pair Options, Pair line at quantity 1 and `$139.00`. The normal populated cart closed and returned focus to the original Choose options trigger. Regression risk is a future product-form change again leaving the submitted input out of sync with the visible selected variant; the VM and browser checks cover that path.

The second seeded issue allowed repeated add-to-cart submissions while the first request was pending. A normal visible double click produced one added item in the observed browser flow, but the controlled VM reproduction exposed two submits before the first request settled. This can create an unintended extra quantity when an event reaches the form twice. `aria-disabled` exposes state to assistive technology but does not reject JavaScript submit events. `assets/product-form.js` now tracks an in-flight request with `isSubmitting` and clears it in `finally` after both success and network failure. The actual submit-handler test starts two deferred requests before completion: baseline source starts two requests and changed source starts one. It then resolves one request and rejects a later one, confirming the form clears `isSubmitting` and permits a retry. Regression risk is an additional submission entry point bypassing `isSubmitting`; the controlled request test covers success and network failure. A browser request-failure or race simulation was not performed.

The third seeded issue blocked mobile navigation from a collection-card image. In Safari Responsive at 393 by 852, tapping the Assessment Compare At Price image on `/collections/all` left the shopper on the collection page, while the title opened `/products/assessment-compare-at-price` correctly. Desktop image navigation passed. This prevents mobile shoppers from opening the product from its main visual and harms product discovery and conversion. In `assets/component-card.css`, the mobile rule at 749px and below gave `.card__heading a::after` a `z-index` of `-1`, placing the card-link overlay behind the card. The fix removes those six lines so the normal overlay remains active. In the Draft preview at Safari Responsive 393 by 852, tapping the image opened `/products/assessment-compare-at-price` and the matching product title. Regression risk is a later card or wishlist overlay taking the tap target; live checks should cover neighbouring card overlays and any wishlist overlay.

The global Theme settings Cart Quick add desktop and tablet choice was enabled as Drawer only on the unpublished development theme. Popup remains the existing default. Drawer applies at 750px and above, while mobile at 749px and below keeps the popup. The selected button price is shown only for the drawer. In Safari Responsive at 750 by 852, Assessment Single and Pair Options opened as a right-side drawer. Its Add to cart button showed `$79.00 USD` for Single and `$139.00 USD` after selecting Pair. In Safari Responsive at 393 by 852, it opened as the existing popup; selecting Pair showed `$139.00 USD` in the product details while the Add to cart button had no price. Closing that popup returned focus to the original Choose options trigger. Fully sold-out collection controls were disabled. Regression risk is a breakpoint or setting change selecting the wrong presentation; the recorded 750 and 393 checks cover the current Drawer setting, while the Existing popup setting should be retested after future theme-editor changes.

The quick-add drawer also adds lifecycle safeguards. `assets/quick-add.js` owns each load with an `AbortController`, ignores stale responses, and only resets the opener for its active request. It renders localized error text and a View product details link when loading fails. Four actual-method VM tests confirm that an older response cannot open over a newer product request, an older `finally` cannot clear the same opener's new loading state, a fetch error creates the localized alert and details link then resets the button, and closing aborts the request without reopening the modal. A fifth actual-method VM regression test covers Escape events that expose `event.key` while `event.code` is unavailable. Safari testing of the deployed feature found that Escape left the visible drawer open even when a real Pair option had focus. The local `assets/quick-add.js` fix listens on the drawer for either `event.key` or `event.code`, prevents the handled event, and hides the drawer. This fix is locally verified by 8 VM tests and was synced as the only changed asset to unpublished development theme `158335795338`. After the Development editor saved the Drawer setting, Safari Responsive confirmed the 750px drawer and selected button prices, and the 393px popup with no button price. Safari Web Inspector confirmed the loaded component exposes `handleKeydown`. Five quick-add elements existed and one was the active `[open]` drawer. A temporary, cancelable keydown on that active drawer with `key` and `code` set to Escape closed it and restored focus to the saved opener. The CUA Escape control produced no captured page keydown even with the Pair radio focused, so its earlier visible non-close was an automation key-delivery limitation, not a confirmed source defect. Browser testing did not simulate loading failures or stale-request races; the actual-method VM tests cover those paths. Physical devices, Chrome, Firefox, Edge, real screen-reader use, and locale checks remain pending. Do not publish or modify the live Shopify theme.
